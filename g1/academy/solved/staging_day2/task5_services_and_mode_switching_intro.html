§1Knowledge — what to call for what

Four different questions, four different getters — there is no separate get_mode() or get_services(); get_state() and get_service() already cover that ground.

CallReturns
g1.get_lowstate()a snapshot dict of every motor (q, dq, tau_est, ...) and the IMU, from the latest LowState_ message
g1.get_odom()the robot's current pose/twist from the odometry topic
g1.get_battery()battery percentage and related BMS fields
g1.get_state()the composite view — FSM id/mode/motion_mode/gait, plus battery, lowstate, services, and SLAM info, all in one call

§2Knowledge — services: list, toggle, set

CallDoes
g1.get_service()returns every known service as {"name","description","status","protected"}
g1.get_service(name)returns just that one row (or None)
g1.toggle_service(name)flips a service based on its current reported status
g1.set_service(name, enabled)sets an explicit on/off instead of flipping — prefer this when you know the target state

See mappings_and_constraints.html §7 for the full catalog: ai_sport, basic_service, g1_arm_example, vui_service, unitree_slam.

ServiceList times out (code 3104) — raise the timeout once. Every service call (get_service/set_service/toggle_service/toggle_dev_mode), and get_state(), goes through the mainboard's ServiceList RPC, whose default 2 second timeout frequently returns 3104 (RPC timeout). Fix it with one line right after constructing G1: g1._robot_state_client().SetTimeout(10.0) — exactly what academy/visualizations/service_view.py does.

§3Knowledge — the full FSM table

Do not invent an id beyond this table. This academy's G1 units run waist-locked (only WaistYaw is a free joint), so walk/balanced-stand is FSM 500, not the waist-unlocked variant's 501.

IDNameTypical use
0Zero-Torquemotors off — safe to handle legs
1Dampviscous damping only (soft) — default power-on, always-available fallback
2unlabeled / "airborne"NOT a confirmed squat mode — do not map this id
3Sitdog-sit posture
4Stand-up / preparefirmware-defined stand, good after Damp
500Start / walkbalance controller & gait planner (waist-locked units)
802Runrunning gait

This course's FSM_IDS = {"zero_torque": 0, "damp": 1, "prepare": 4, "walk": 500, "run": 802} covers the five you'll actually call via damp_mode()/prepare_mode()/walk_mode()/run_mode().

Ids 702/706 are not confirmed for this hardware — academy/mappings_and_constraints.html (this repo's own audited FSM reference) does not list them. Treat only 0/1/3/4/500/802 as verified.

§4Knowledge — the safe mode ladder

damp_mode() (FSM id 1) is always available: bounded joint damping, no locomotion authority. Always step damp_mode() → prepare_mode() → walk_mode(), one at a time, checking get_state() between steps — never jump straight to run_mode(). toggle_dev_mode() flips the ai_sport service; several Day 3 low-level control calls need dev mode enabled first.

§7Task 2 — prove vui_service gates audio

vui_service is the robot's Audio and Lighting Control Service — say() and set_headlight() both depend on it. Turn it off, call say() (you will hear nothing), then turn it back on and say() again (audio works). set_service(name, enabled) sets an explicit on/off; get_service(name) reads status (0 = ON, non-zero = OFF). The setup cell already raised the RPC timeout, so these calls don't fail with 3104.

§9Final part — build a mode-switching dashboard with Codex

You have now driven every FSM transition by hand. The last exercise is to wrap those same g1 calls in a small web dashboard — not by writing it yourself, but by prompting Codex to build it against sdk_wrapper.G1. A finished reference already runs on this robot: academy/visualizations/mode_control.py, the mode-control dashboard served on port 8051. Open it in your browser first to see the target — one button per mode, a live state line, and buttons that grey out when a transition would be unsafe — then have Codex produce your own version on a different port so the two don't clash.

Example prompt for Codex (adjust to taste; read the generated file before running it):

Using the G1 class in academy/sdk_wrapper.py, write a Dash + dash-bootstrap-components
web app mode_switch_dashboard.py that mirrors academy/visualizations/mode_control.py
(the mode-control dashboard already running on port 8051). Requirements:
- Construct a single G1(iface="eth0", domain_id=0) instance at startup and reuse it for
  every callback, guarded by a threading.Lock; never build more than one G1 per process.
- One large button per FSM mode -- Zero Torque, Damp, Prepare, Walk, Run -- each calling
  the matching wrapper method: g1.zero_torque_mode(), g1.damp_mode(), g1.prepare_mode(),
  g1.walk_mode(), g1.run_mode(). Add a red Stop button wired to g1.loco_stop().
- A once-per-second dcc.Interval callback that reads g1.get_state() and shows the live
  id / mode / motion_mode / gait and battery soc in a status line, with the raw dict in
  a <pre> block.
- Enforce the safe mode ladder: always allow Damp; disable Walk/Run unless the current
  mode is already prepare/walk/run. Wrap every robot call in try/except so one failed
  RPC never kills the app, and show the error text in the status line.
- Bind to host 0.0.0.0 on port 8052 (a new port, so it does not clash with the 8051
  dashboard) and print the URL on startup.

Run it from a terminal with python3 mode_switch_dashboard.py --port 8052 and open http://<robot-ip>:8052. This is the same Dash pattern Day 3's end-effector teleoperation dashboard (Task 3) reuses.
