Knowledge Task 5

Knowledge — what to call for what

Four different questions, four different getters — do not conflate them.

CallReturns
g1.get_lowstate()a snapshot dict of every motor (q, dq, tau_est, ...) and the IMU, from the latest LowState_ message
g1.get_odom()the robot's current pose/twist from the odometry topic
g1.get_battery()battery percentage and related BMS fields
g1.get_state()the composite view — FSM id/mode/motion_mode/gait, plus battery, lowstate, services, and SLAM info, all in one call
g1.get_service(name=None)every registered service (no args), or one named row
Read state before you act on it: check get_state() between every mode-switching step below, rather than assuming a call succeeded because it didn't raise.
Knowledge Task 5

Knowledge — the full FSM table

Do not invent an id beyond this table. Confirmed by this course's FSM_IDS and academy/mappings_and_constraints.html (cross-checked against sdk_wrapper.py and other academy scripts): 0/1/3/4/500/802. This course's G1 units run waist-locked (only WaistYaw is a free joint), so walk/balanced-stand is FSM 500; 501 is the same state on waist-unlocked (3-DOF waist) units and does not apply to this hardware. Id 2 is NOT confirmed — mappings_and_constraints.html traces it to an unlabeled/"airborne" placeholder (fsm_2_squat_placeholder in dev code) and explicitly warns not to map an undocumented FSM ID; do not send it expecting a squat. Ids 702/706 do not appear anywhere in this repo's own FSM reference either — treat any claim about them as unverified until confirmed against your unit's firmware, not as something safe to script against.

Knowledge Task 5

Knowledge — damp as the universal fallback, dev mode, and a dashboard target

g1.damp_mode() (FSM id 1) is the one mode this course treats as always available: bounded joint damping, no locomotion authority.

  • Call damp_mode() before an emergency stop, and before switching to a different mode — always step damp_mode() → prepare_mode() → walk_mode(), one at a time, never straight to run_mode().
  • g1.toggle_dev_mode() flips the ai_sport service; several Day 3 low-level control calls need dev mode enabled first.
  • g1.set_service(name, enabled) sets an explicit on/off instead of flipping — prefer it over toggle_service when you know the target state you want.

One call, loco_move(vx, vy, vyaw, duration_s), does the driving. The task is chaining a few of them into a path you can reuse tomorrow.

Knowledge Task 6

Knowledge — loco_move's timing

g1.loco_move(vx, vy, vyaw, duration_s=2) sends a continuous velocity command, blocks for duration_s, then calls loco_stop() for you automatically.

CallBehavior
loco_move(vx, vy, vyaw, duration_s=2)drives for exactly duration_s seconds, then auto-stops — the common case
loco_move(vx, vy, vyaw, duration_s=None)fires one Move() RPC and returns immediately, no auto-stop — only use this when you are managing the stop yourself
loco_stop()stops immediately — call any time you need to bail out of a move early
vx/vy are in m/s (forward/strafe), vyaw in rad/s. Start small (e.g. 0.15 m/s) with a spotter in a clear space.
Knowledge Task 6

Knowledge — chaining moves into a path

  • A path is just several loco_move(...) calls back to back — e.g. forward, turn, forward, turn, forward traces an approximate "U" shape in 3 legs.
  • Keep the stop points as data (a list), and let a small callback run at each stop — this is exactly the hook Day 3's Task 1 reuses to play a different arm gesture at each stop of the same U path.
  • get_odom() before and after each leg is your ground truth for how far the robot actually went — open-loop timing drifts, so do not assume duration_s and commanded velocity alone give you exact distance.

Solution Task 6

Solution — walk_u_path with a stop hook

The reusable part for Day 3 is the on_stop(g1, i) hook — today it does nothing (or prints), tomorrow it plays a gesture.

import time  # for pause_s below

def walk_u_path(g1, vx=0.15, vyaw=0.5, leg_s=2.0, turn_s=1.2, pause_s=1.0, on_stop=None):
    legs = [(vx, 0.0, 0.0, leg_s), (0.0, 0.0, vyaw, turn_s),
            (vx, 0.0, 0.0, leg_s), (0.0, 0.0, vyaw, turn_s),
            (vx, 0.0, 0.0, leg_s)]
    stop_index = 0
    for i, (lvx, lvy, lvyaw, duration_s) in enumerate(legs):
        g1.loco_move(lvx, lvy, lvyaw, duration_s=duration_s)
        if i % 2 == 0:  # after each straight leg, we are at a stop point
            if on_stop is not None:
                on_stop(g1, stop_index)
            time.sleep(pause_s)
            stop_index += 1
    g1.loco_stop()

Knowledge Task 7

Knowledge — named points and navigation

g1.add_map_pose() appends the current SLAM pose to the wrapper's own path queue (consumed by g1.navigate()), but does not name it. To come back to a spot by name later, save it yourself — a tiny JSON dict of {"{name: [x, y, yaw]}"} on disk, keyed off g1.get_slam_pose(). That is exactly what g1.navigate_to_point(point_name, points_path="slam_points.json") expects to read.

CallDoes
g1.navigate_to_point(name, points_path=..., timeout_s=120.0)reads the named pose, sends it, blocks until arrival or timeout
g1.pause_nav() / g1.resume_nav()interrupt / continue an in-progress navigation
g1.loco_stop()immediate full stop, including mid-navigation

Solution Task 7

Solution — named points, and seeing the map

import json
from pathlib import Path

def add_point(g1, name, points_path="slam_points.json"):
    path = Path(points_path)
    points = json.loads(path.read_text()) if path.exists() else {}
    points[name] = list(g1.get_slam_pose())
    path.write_text(json.dumps(points))
    return points[name]

def remove_point(name, points_path="slam_points.json"):
    path = Path(points_path)
    points = json.loads(path.read_text()) if path.exists() else {}
    points.pop(name, None)
    path.write_text(json.dumps(points))
