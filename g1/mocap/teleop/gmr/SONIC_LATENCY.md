# Moretion → GMR → SONIC 本地仿真延迟修复

2026-10-13 修订：上一版虽然消除了参考播放积压，但将未知未来窗口全部填为当前
姿态，默认模型走路时的滑步反馈表明这种默认设置过于激进。当前版本优先保留真实
动作预览，再去掉额外积压；下方保留上一版测量，以区分参考传输延迟与动作还原度。

## 原因

主要延迟在 SONIC 的参考轨迹播放游标，和更换 ONNX 模型无直接关系。

1. SONIC `G1Deploy` 先用 `duration_(3.0)` 做 3 秒站姿初始化。
   此时输入线程已经接收和合并 GMR 动作，控制线程尚未推进参考播放游标。
   开始控制后发送和播放均为 50 Hz，启动积压不会自行消失。
   `catch_up=true` 只允许合并器在间隔超过约 205 帧（4.1 秒）时追赶，
   所以约 3 秒的积压可以一直保留。用户较晚开启跟踪时，积压可能较小。
2. GMR 原来默认发送最近 5 个历史样本，SONIC 却将它作为未来轨迹播放。
   观察量需要当前帧之后的参考姿态，`CurrentFrameAdvancement()` 会为这些姿态保留尾部帧。
   默认 G1 编码器为 `10frame_step5`，需要 46 个样本；低延迟 G1 编码器为
   `10frame_step1`，需要 10 个样本。缺少未来姿态时等待真实输入，会形成约
   0.92 秒或 0.20 秒的参考延迟。它与启动积压共同约束播放位置，并非简单相加。
3. GUI 原来未启用 pose 订阅器的 ZMQ CONFLATE；订阅线程被阻塞时还可能排队。
   降低模型推理时间不会修复上述游标和参考窗口问题。

Moretion 使用 Protocol v1 的 G1 关节编码器；低延迟配置中 SMPL 的 4 帧设置
不适用于这条关节输入路径。

## 当前方案：保留真实预览，限制额外积压

GUI 和脚本现在默认使用 `--reference_mode preview`。界面默认使用折中预览：
默认模型 400 ms，低延迟模型 100 ms，切换模型会重设为对应折中值。
仍可手动修改预览延迟；选择 -1（“按模型保留完整预览”）恢复下表的完整预览。
直接运行脚本且不指定 `--preview_delay_ms` 时仍保留完整预览：

| 模型 | 编码器需要的未来位置 | 完整真实预览延迟 | 完整预览参考输出延迟 P50 / P95 |
| --- | --- | --- | --- |
| 默认 | 当前及后续 45 帧，10 个 step5 样本 | 920 ms | 937.1 / 938.2 ms |
| 低延迟 | 当前及后续 9 帧，10 个 step1 样本 | 200 ms | 226.4 / 227.1 ms |

完整预览多保留一帧，用于末端真实前向关节速度。这样当前及未来位置、速度、
根姿态都来自已经收到的动作，不再将整个步态窗口伪造成静止状态。
只等待这一段固定预览，不播放初始化过程中累积的所有旧动作。
`live_frame_index` 标记的是最新样本减去预览时长后的目标帧；部署端仍每次收包
对齐该帧，启动等待、网络排队和丢包不会在预览时长之外持续增加积压。

历史前缀已从目标帧之前 4 帧精简为 1 帧：`--batch` 默认 2，表示
“1 帧历史 + 目标帧”，不包含后面的预览窗口。零预览仍可用前一帧估计速度。
每包继续携带目标帧及模型所需的未来参考，目标帧之后的位置、速度、根姿态
与精简前完全一致。50 Hz 下当前界面折中设置的窗口为：

| 模型 | 本地真实样本缓存 | 每包参考帧数（精简前 → 后） |
| --- | --- | --- |
| 默认，400 ms | 22 帧 | 50 → 47 |
| 低延迟，100 ms | 7 帧 | 14 → 11 |

完整预览时，每包分别为 48 / 12 帧（含末端求速度用的额外样本）。减少历史
只降低重复传输和拷贝，不改变 400 / 100 ms 的预览延迟。跳过消息后下一包
仍携带完整参考窗口；长时间断流时不能靠这一帧历史保证连续动作。

GUI 新增“动作预览延迟”。自动值为上述两个默认设置，选择低延迟模型时，GMR
发送端和部署端同时使用对应模型配置。自定义值向上取整到 20 ms 控制周期：

- 默认模型可以用 400–600 ms 作为较短预览的对照值，但这会缺少部分真实未来。
- 低延迟模型可以用 100–160 ms 作对照；保留完整预览时用自动值或 200 ms。
- 0 ms 等同上一版最新姿态保持。不建议将其作为默认模型走路的默认设置。

短预览保留能获得的真实未来样本，只对缺失尾部保持姿态；缺失尾部速度为零。
这些自定义值属于还原度和延迟的取舍，不是已验证的通用最优值。没有改模型权重、
训练时的观察时间步或电机增益，也没有加入长期动作预测。
只运行重定向时，模型与预览设置可编辑，通过标准输入同步给运行中的发送端，
无需重启 IK 或重定向窗口。窗口增大时等待新增的真实预览样本；窗口缩小时保留
最近的样本。启动部署前再次同步设置，部署连接期间锁定，避免两端窗口不匹配。

对任意未知的实时动作，在保持默认模型原有输入语义、且不预测未来的条件下，
约 0.9 秒未来位置无法在 20 ms 内真实获得。需要更短延迟而仍保留完整预览时，
优先使用低延迟模型，而非缩放默认模型的时间轴。

## 上一版改动：最新姿态保持（现在仅作为显式对照模式）

- 上一版 GMR 默认使用 `--reference_mode live`：保留最近 5 帧历史以计算关节速度，
  从第一帧开始发送，并增加 `live_frame_index` 明确标记最新实际样本。
- 将最新关节位置、根姿态保持为后续 49 个参考样本，未来关节速度置零。
  这是未知未来姿态的保持值，不是等待真实未来动作，也没有对动作作无界外推。
  当前样本及保持值覆盖两种 G1 模型需要的观察窗口。
- SONIC 解析当前帧标记，每次收包将播放游标对齐最新样本，消除初始化积压、
  丢包和调度暂停造成的历史播放延迟。历史窗口重叠不重置朝向校准；发送端
  真正重启或时间轴回退时重新校准。
- GUI 默认启用 `--zmq-conflate`，仅作用于 pose 订阅器，command 订阅器保持原来的行为。
- 输出线程暂停时按实际经过的控制周期推进索引，并重建连续帧窗口；
  计算速度时使用帧索引对应的时间差。
- 未包含 `live_frame_index` 的已有发送端保持原来的轨迹播放行为。
  GMR 可通过 `--reference_mode buffered` 使用旧路径作对照。

本次同时修改 GMR 和相邻 SONIC 部署仓库。发送端和部署程序应一起更新；
只更新 GUI 或只替换模型不足以启用当前帧对齐。

## 验证与限制

当前预览版本通过 28 项 Python 检查及 8 项 C++ 回归用例。新增检查确认精简历史后，
两种模型在零预览、折中预览、完整预览下的目标及未来输入与精简前逐项一致；
部署端跳过消息、遇到较长间隔或发送端重启后，下一包仍提供完整编码器参考。
本次历史精简复测时 Moretion 服务拒绝连接，未重复进行实时动捕联调；下方实时
动捕与 MuJoCo 数值为此前测量。
新增检查覆盖两种模型的真实位置/速度预览、预热后游标单调推进、短预览、
0 ms 对照、丢包后的有界延迟，以及 GUI 模型与发送窗口一致性。

在 SONIC 自带走路样例 `walking_quip_360_R_002__A428` 上，将送给编码器的
10 个时间点逐项与实际未来轨迹比较：

| 模型 | 预览设置 | 未来位置 RMSE (rad) | 未来速度 RMSE (rad/s) |
| --- | --- | --- | --- |
| 默认 | 上一版保持，0 ms | 0.2479 | 1.2674 |
| 默认 | 短预览，400 ms | 0.1673 | 0.9547 |
| 默认 | 完整预览，920 ms | 0 | 0 |
| 低延迟 | 上一版保持，0 ms | 0.1103 | 1.1660 |
| 低延迟 | 短预览，100 ms | 0.0401 | 0.7853 |
| 低延迟 | 完整预览，200 ms | 0 | 0 |

这里的零误差只表示参考窗口保留了已收到的真实轨迹，不代表机器人实际关节跟踪
误差为零。上表说明短预览的输入失真，并非对实际滑步程度的直接测量。

当前默认预览的输出延迟使用真实 ONNX 编码器/解码器及 MuJoCo 测量，方法与下面
上一版对照相同。它不再追求上一版约 16 ms 的参考输出数字，而是保留完整未来
信息，同时把原有约 3 秒积压压到模型所需的固定预览时长。

还使用上述步行样例，在 MuJoCo 中释放虚拟悬挂带，对真实 ONNX 模型做步行对照。
按相同参考步态帧（第 100–349 帧，共 250 个控制样本）比较 12 个腿部关节：

| 模型 | 预览设置 | 部署参考延迟 P50 | 实际腿部跟踪 RMSE (rad) |
| --- | --- | --- | --- |
| 默认 | 上一版保持，0 ms | 17 ms | 0.1933 |
| 默认 | 短预览，400 ms | 428 ms | 0.0928 |
| 默认 | 完整预览，920 ms | 942 ms | 0.1017 |
| 低延迟 | 上一版保持，0 ms | 20 ms | 0.1881 |
| 低延迟 | 短预览，100 ms | 126 ms | 0.1382 |
| 低延迟 | 完整预览，200 ms | 231 ms | 0.1144 |

完整预览改善了这段样例的实际跟踪。默认模型 400 ms 在此样例上也是有效折中，
但不能从一个样例推断它对所有步态都优于完整预览。可先用默认模型 400 ms、
低延迟模型自动 200 ms 做现场对照；出现滑步时恢复完整预览，而不是进一步减小。

同一中段步行区间的接触脚平均水平速度仍约为 0.064–0.072 m/s，变化较小，
因此不能声称滑步完全消除。该样例末端/转场仍出现失稳，以上关节误差比较限于
中段正常步行，不能证明停步、急转或任意 Moretion 动作的稳定性。

2026-10-13 的 Moretion 实时检查已收到 `192.168.2.45:9999` 的动作流：源端约
60 Hz，GMR 到 SONIC 输出约 50 Hz。实际检查到默认模型 256 个消息、低延迟模型
201 个消息，预览分别保持 46 帧及 10 帧固定间隔；两个编码器中的关节速度与对应
真实相邻参考帧的前向差分误差均为零。该检查验证实时数据路径，
没有据此宣称现场人体走路的滑步问题已经完全解决。

## 使用

部署端已有 `live_frame_index` 支持，本轮无需修改模型或部署端播放实现。
关闭并重新打开 Teleop Studio，设置 Moretion 地址为
`192.168.2.45`，选择本地部署和 MuJoCo 仿真目标；默认与低延迟模型都可以使用。
先选好模型和预览延迟，再按原有顺序启动重定向、部署和跟踪。
MuJoCo 仍通过 `bash scripts/run_sonic_sim.sh` 启动；仿真代码未改动，无需调整电机增益。
走路检查还应确认 MuJoCo 中虚拟悬挂带已经释放（按 9 切换）；该仿真默认启用
虚拟弹簧，它会限制根位置，不能把悬挂状态下的滑步归因于策略延迟。

命令行使用低延迟模型时，发送端也要明确选择对应预览窗口：

```bash
python scripts/moretion_stream_to_sonic.py --server_ip 192.168.2.45 --model_profile low_latency --vis
```

默认模型完整预览省略 `--model_profile`，较短预览通过 `--preview_delay_ms 400` 显式指定。
